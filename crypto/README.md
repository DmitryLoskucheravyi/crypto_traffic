# CRYPTO SPHEERE — архитектура

Монорепозиторий на npm workspaces из двух независимых приложений и базы:

| Часть     | Где        | Что это                                                        |
| --------- | ---------- | -------------------------------------------------------------- |
| Лендинг   | `apps/web` | Статический сайт на Next.js (`output: 'export'`), отдаёт nginx |
| Бот       | `apps/api` | NestJS + Telegraf: продажа курсов и приём USDT TRC20           |
| Хранилище | MongoDB    | Только заказы бота                                             |

Лендинг и бот не связаны в рантайме: страница не делает ни одного запроса к
API, а все её кнопки ведут в Telegram. Цена существует только в боте.

```
 браузер ──► nginx (статика apps/web/out)
                │ ссылки
                ▼
 Telegram ◄──► apps/api ──► MongoDB (orders)
                  │
                  └──► TronGrid (входящие USDT TRC20 на кошелёк)
```

## apps/api — бот и платежи

### Слои

```
src/
├── main.ts                 composition root: читает окружение, собирает AppModule
├── app.module.ts
├── config/                 конфигурация
│   ├── app-config.ts         loadConfig(env) → AppConfig — чистая функция
│   └── config.module.ts      отдаёт AppConfig через DI (токен APP_CONFIG)
├── catalog/catalog.ts      каталог курсов: данные + чистые функции
├── payments/
│   ├── domain/             предметная область — без Nest, Mongo и часов
│   │   ├── amount.ts         уникальная сумма заказа, сравнение сумм в BigInt
│   │   ├── order.ts          Order, newOrder(), isAwaitingPayment(), isPayableBy()
│   │   └── transfer.ts       Trc20Transfer
│   ├── order.repository.ts порт хранилища (абстрактный класс = DI-токен)
│   ├── mongo/              адаптер порта: схема и MongoOrderRepository
│   ├── tron/               адаптер TronGrid
│   │   ├── trongrid.ts       сборка запроса и разбор ответа — чистые функции
│   │   └── trongrid.client.ts  только HTTP
│   ├── order-events.ts     событие «заказ оплачен» (observer)
│   ├── payments.service.ts сценарии заказа: выставить, отменить, просрочить, оплатить
│   └── tron-watcher.service.ts  периодический опрос кошелька
├── telegram/
│   ├── telegraf.provider.ts  единственное место, где создаётся Telegraf
│   ├── bot-runner.service.ts жизненный цикл: запуск, перезапуск, остановка
│   ├── bot.handlers.ts       маршрутизация команд и кнопок → сценарии
│   ├── delivery.service.ts   выдача оплаченного курса в чат
│   ├── texts.ts              тексты сообщений — чистые функции
│   ├── keyboards.ts          клавиатуры и формат callback_data — чистые функции
│   └── materials.ts          разбор COURSE_MATERIAL_* → путь / URL / file_id
├── health/                 GET /api/health
└── testing/                in-memory адаптеры и конфиг для тестов (в сборку не входят)
```

Зависимости направлены внутрь: `domain/` не импортирует ничего, кроме
каталога. Сервисы зависят от домена и от портов, адаптеры (Mongo, TronGrid,
Telegraf) реализуют порты и подключаются только в модулях.

### Принципы

- **Единственная ответственность.** Каждый класс отвечает за одно:
  `PaymentsService` — сценарии заказа, `OrderRepository` — хранение,
  `OrderEvents` — оповещение, `TronGridClient` — HTTP, `TronWatcherService` —
  расписание, `BotRunner` — жизненный цикл бота, `BotHandlers` — маршрутизация,
  `DeliveryService` — выдача материалов.
- **Инверсия зависимостей.** `PaymentsService` знает только абстрактный
  `OrderRepository`. В проде это `MongoOrderRepository`, в тестах —
  `InMemoryOrderRepository`. Конфиг, экземпляр Telegraf и хранилище приходят
  через конструктор, ни один класс не создаёт свои зависимости сам.
- **Чистое ядро, эффекты на краях.** Правила — чистые функции без ввода-вывода
  и без неявного времени (`now` передаётся аргументом): подбор суммы, окно
  оплаты, разбор ответа TronGrid, тексты, клавиатуры, конфиг. Сеть, база и
  Telegram живут только в адаптерах.
- **Один источник правила.** Какой перевод оплачивает какой заказ, описывает
  `isPayableBy` / `paymentWindow` в `domain/order.ts`. Mongo-адаптер строит
  запрос из того же `paymentWindow`, in-memory-адаптер вызывает сам
  `isPayableBy`.
- **Конфиг один раз.** `process.env` читается только в `main.ts`. Дальше
  неизменяемый `AppConfig` раздаётся через DI.
- **Развязка модулей событиями.** Платежи публикуют «заказ оплачен» в
  `OrderEvents`, Telegram подписывается. `payments/` ничего не знает о боте.

### Модель оплаты

Кошелёк один на всех, поэтому платёж опознаётся по сумме, а не по отправителю.
Каждый заказ получает базовую цену с уникальным «хвостом» в четвёртом знаке
(`10` → `10.0304`), это 9999 одновременных заказов на уровень. Уникальность
среди ожидающих держит частичный уникальный индекс Mongo по `amountKey`.

Суммы сравниваются строками-ключами, полученными целочисленной арифметикой
(`BigInt`): в `double` число `10.0304` непредставимо, и округление увело бы
платёж к соседнему заказу. Пыль ниже четвёртого знака отбрасывается.

Жизненный цикл заказа:

```
pending ──(перевод в окне)──► paid ──► notified ──► delivered
   │ ▲
   │ └── expired (поздно увиденный перевод, отправленный до конца срока, всё равно оплачивает)
   └──► cancelled
```

Гарантии:

- перевод оплачивает заказ, только если отправлен между созданием заказа и
  концом его срока (по времени блока, с запасом на расхождение часов);
- одна транзакция закрывает не больше одного заказа (проверка `txId`);
- перевод в `paid` — атомарный `findOneAndUpdate`, поэтому пересекающиеся
  проходы слушателя не закроют заказ дважды;
- выдача идемпотентна: флаги `notified` и `delivered` плюс блокировка на заказ
  внутри процесса; неотправленное догоняется при каждом запуске бота.

### Устойчивость

- Ошибка в хендлере ловится `bot.catch` и не останавливает long-polling.
- Без связи с Telegram сервис стартует, а бот перезапускается каждые 30 с.
- Недоступность TronGrid гасится в клиенте: проход слушателя вернёт пустой
  список и повторится.
- Слушатель не запускает новый проход, пока не закончен предыдущий.

## apps/web — лендинг

Статический экспорт Next.js (App Router). На выходе `out/` — готовые файлы без
Node-процесса. Контент запекается на сборке.

```
app/
├── layout.tsx, page.tsx    каркас страницы, метаданные, Schema.org
├── robots.ts, sitemap.ts   генерируются на сборке
├── lib/
│   ├── config.ts             публичный конфиг: buildPublicConfig(env) — чистая функция
│   ├── content.ts            тексты интерфейса
│   ├── site-data.ts          структурированные данные: уровни, этапы, калькулятор…
│   ├── structured-data.ts    граф Schema.org из тех же данных
│   ├── calculator.ts         расчёт калькулятора дохода
│   ├── format.ts             форматирование чисел
│   ├── charts/               генерация графиков: ломаные, свечи, маршруты по сетке
│   ├── seeded-random.ts      детерминированный PRNG
│   └── motion.ts             общие константы анимации
└── components/
    ├── sections/             секции страницы
    ├── effects/              декоративные слои (фон hero, курсор, прогресс)
    ├── ui/                   переиспользуемые элементы
    └── icons/                SVG-иконки на общей базе
```

Принципы:

- **Данные отдельно от представления.** Тексты — в `content.ts`, данные — в
  `site-data.ts`, ссылки и адрес сайта — в `config.ts`. Компоненты только
  рисуют то, что получили из `lib/`.
- **Логика отдельно от компонентов.** Расчёты калькулятора, форматирование и
  генерация графиков — чистые функции в `lib/`, покрытые тестами. В
  компонентах остаются состояние и анимация.
- **Детерминизм.** Все «рыночные» визуализации сгенерированы из фиксированных
  seed'ов: серверная и первая клиентская отрисовка совпадают байт в байт,
  реальных котировок на странице нет.
- **Конфиг только на сборке.** `NEXT_PUBLIC_*` читаются один раз в `config.ts`.
  Пустое значение равнозначно незаданному, так что сборка без домена
  собирается с локальным фолбэком.
- **Ноль запросов в рантайме.** Тест проверяет, что в `app/` нет `fetch` и
  обращений к API.

## Поставка

| Образ / артефакт | Сборка                                                         |
| ---------------- | -------------------------------------------------------------- |
| `api`            | `node:20-alpine`, зависимости по корневому `package-lock.json` |
| `web`            | сборка на Node, рантайм — `nginx:alpine` со статикой           |
| `mongo`          | `mongo:7`, том `mongo-data`                                    |

- Материалы курсов — платный контент. Они не лежат в git и не попадают ни в
  образ, ни в контекст сборки: `./materials` монтируется в контейнер бота
  томом только для чтения.
- CI: формат → типы → тесты → сборка на каждый пуш. Release по тегу `v*`:
  образ бота в GHCR и архив статики лендинга.
